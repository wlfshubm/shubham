Building Black Cat

Aug 2026

Black Cat started as a simple question: could I build a Discord music bot that actually held up once real servers started using it, instead of falling over the moment more than a handful of people queued songs at once?

The core problem

Most small Discord bots are written as a single process handling every server it's in. That works fine at a small scale, but the moment you're running across many large servers with long queues and concurrent playback, a single process becomes a bottleneck — and a single point of failure. I wanted Black Cat to be sharded from early on, so the bot could scale horizontally instead of hitting a wall.

What I ended up building

The finished bot is a full playback engine — queues, audio filters, and per-user favorites — wired through Lavalink for stable, high-quality audio streaming. On top of playback sits an automod system, so server owners get some moderation help without having to babysit chat themselves. I also added custom profile and song cards rendered per user, and a web dashboard for controlling the bot outside of Discord entirely.

The stack

Node.js and Discord.js handle the core bot logic. Lavalink does the heavy lifting for audio streaming, which kept the bot itself lightweight since it doesn't have to process audio directly. SQLite stores persistent data — queues, favorites, server settings — since it's simple to run and didn't need a separate database server for this scale.

What I'd do differently

Sharding early was the right call, but it also meant more complexity up front than a single-process bot would have needed. In hindsight, I'd spend more time up front on monitoring and error reporting across shards — debugging an issue that only shows up on one shard, under one specific server's load, is a different kind of problem than debugging a single process.
